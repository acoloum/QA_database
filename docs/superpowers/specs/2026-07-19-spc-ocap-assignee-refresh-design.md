# SPC OCAP 責任人選擇與即時資料更新設計

**日期：** 2026-07-19

**狀態：** 已確認

**範圍：** 出貨檢驗與巡檢頁面共用的 SPC OCAP 操作

## 1. 背景

目前 OCAP 有兩項操作限制：

1. 責任人只能輸入數字使用者 ID，操作者無法從可辨識的人員清單選擇。
2. OCAP 儲存後，畫面失效化了未被使用的 `spcEvents` 與 `spcOcap` 快取鍵；後端又只回傳 ID、事件 ID 與狀態，因此目前版本內嵌的事件仍保留舊 OCAP。關閉後再次開啟時，必須重新整理頁面才會看到最新內容。

既有 `/api/users` 需要 `user.manage` 權限，並包含使用者管理用途的完整資料，不適合直接開放給只有 `spc.manage` 權限的 OCAP 操作者。

## 2. 目標

- 責任人改為可辨識的下拉選單。
- 可指派範圍固定為啟用中的 QA 主管、品管經理與系統管理員。
- 不擴大既有使用者管理 API 的存取權限或資料揭露範圍。
- OCAP 儲存成功後立即更新目前事件，關閉後再次開啟可看到最新資料。
- 保留既有 OCAP 稽核軌跡及歷史責任人，不因帳號停用或角色變更而遺失紀錄。

## 3. 非目標

- 不修改角色或權限模型。
- 不新增或變更資料表，因此不需要資料庫 migration。
- 不開放檢驗員或其他自訂角色成為責任人。
- 不改變 OCAP 的 6M、重新量測、製程調整、產品處置、有效性確認與結案規則。

## 4. 採用方案

新增 SPC 專用責任人查詢端點，而非重用或放寬 `/api/users`。端點只回傳下拉選單必要欄位，並由後端使用相同白名單驗證新指派。

此方案比放寬 `user.manage` 更符合最小權限原則，也比儲存後強制整頁重載更能維持目前 React Query 與父層版本狀態的資料流。

## 5. 後端設計

### 5.1 責任人查詢 API

新增：

```text
GET /api/spc/assignees
權限：spc.manage
```

只查詢 `is_active = true` 且角色代碼屬於下列白名單的使用者：

- `qa_supervisor`：QA主管
- `qc_manager`：品管經理
- `admin`：系統管理員

成功回應沿用 SPC API 的 `data` 包裝格式，每筆只包含：

```json
{
  "id": 12,
  "username": "quality.manager",
  "role": "qc_manager",
  "role_name": "品管經理"
}
```

清單依角色顯示名稱、使用者名稱與 ID 穩定排序。沒有符合人員時回傳空陣列，不視為伺服器錯誤。

### 5.2 指派驗證

建立 OCAP 或變更既有 `owner_id` 時，服務層確認目標使用者存在、已啟用且角色位於白名單；不符合時回傳穩定的 `400 SPC_OCAP_OWNER_NOT_ASSIGNABLE`。

若既有 OCAP 的責任人後來停用或更換角色，僅編輯其他欄位且 `owner_id` 未變更時仍允許儲存。這可保留歷史資料並避免帳號狀態變更阻斷其他 OCAP 維護工作。清除責任人仍沿用目前允許 `null` 的契約。

### 5.3 完整 OCAP 回應

OCAP POST 與 PATCH 成功後改用既有 `serialize_ocap` 回傳完整資料，包括調查、重新量測、調整、處置、責任人、有效性、狀態及建立／更新稽核欄位。前後端共用同一份 `SpcOcapRecord` 契約，不再另設只有三個欄位的摘要型別。

## 6. 前端設計

### 6.1 責任人下拉選單

新增 `useSpcAssignees` 查詢，使用固定快取鍵 `['spcAssignees']`。只有具 `spc.manage` 權限且開啟 OCAP 編輯介面時才需要取得資料。

`SpcOcapOffcanvas` 將數字欄位改成選單：

- 第一項為「未指派」。
- 一般項目顯示「使用者名稱（角色名稱）」。
- 載入中與查詢失敗時提供明確提示；查詢失敗不清除表單其他內容。
- 若現有責任人不在可指派清單，加入一個停用選項「原責任人 ID：n（目前不可指派）」以顯示歷史值；操作者可保留或改選有效人員。

### 6.2 儲存後同步

`useSaveSpcOcap` 回傳完整 `SpcOcapRecord`，並以實際使用的 `['spcStudy', studyId]` 快取鍵重新驗證伺服器資料。

儲存成功時，`SpcStudyPanel` 立即執行不可變更新：

1. 將回傳 OCAP 合併到目前 `selectedEvent`。
2. 在目前 `SpcStudyResult.limit_versions[].events[]` 中依 `event_id` 找到事件並替換其 `ocap`。
3. 透過既有 `onVersionChange` 把更新後版本交回父層。
4. 關閉 OCAP 側欄。
5. React Query 背景重新取得研究資料，作為與後端最終一致性的保險。

因此即使背景查詢尚未完成，再次點擊同一事件也會取得剛儲存的 OCAP，而不依賴整頁重新整理。

## 7. 錯誤與稽核處理

- 沒有 `spc.manage`：`403`。
- 責任人不存在、已停用或角色不符合：`400 SPC_OCAP_OWNER_NOT_ASSIGNABLE`。
- OCAP 或事件不存在：沿用既有穩定錯誤契約。
- 儲存失敗時保持側欄與使用者輸入，不更新父層事件，也不假裝儲存成功。
- 成功儲存仍由 `SpcOcapService` 在同一交易中記錄完整舊值與新值，責任人變更納入既有 audit log。

## 8. 測試策略

採測試先行，至少涵蓋：

### 後端

- `spc.manage` 可取得責任人清單，無權限者收到 `403`。
- 只回傳啟用中的 `qa_supervisor`、`qc_manager`、`admin`，排除檢驗員、停用帳號及其他角色。
- 新增或變更為不可指派責任人時拒絕，且不寫入 OCAP 或 audit log。
- 原責任人後來不可指派時，未變更責任人仍可編輯其他欄位。
- POST 與 PATCH 都回傳完整 OCAP 契約。

### 前端

- 責任人顯示使用者名稱與角色，而非要求輸入數字 ID。
- 現有不可指派責任人以停用歷史選項顯示。
- 儲存成功後目前版本的對應事件立即取得新 OCAP。
- 關閉並重新開啟相同事件時顯示最新值。
- 儲存失敗時保留表單內容並顯示錯誤。
- mutation 失效化實際的 `spcStudy` 快取鍵，不再使用不存在的舊鍵。

## 9. 驗收標準

- 出貨檢驗與巡檢的 OCAP 責任人皆可從同一份 QA 角色清單選擇。
- 一般 OCAP 管理者不需要取得 `user.manage` 權限。
- 後端不能透過手動 API 請求指派停用帳號或非白名單角色。
- 儲存 OCAP 後不重新整理頁面，關閉再開啟仍看到最新內容。
- 歷史責任人不會因帳號停用或角色變更而消失。
- 後端測試、前端測試、lint、build 與 `git diff --check` 全部通過。

## 10. 已確認決策

1. 可指派人員限啟用中的 `qa_supervisor`、`qc_manager`、`admin`。
2. 採 SPC 專用唯讀責任人端點，不放寬 `/api/users`。
3. API 儲存成功回傳完整 OCAP，前端立即合併並背景重新驗證。
4. 不需要資料庫 migration。
