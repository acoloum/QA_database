# 機械性質檢驗獨立追溯編號設計

**日期：** 2026-07-23
**狀態：** 已核准
**範圍：** 機械性質檢驗 Phase 1.1

## 背景

目前機械性質檢驗以「機械性質批次」子表，把「擠製編號」與「爐具編號」放在同一列，畫面也以成對欄位新增。

實際製程中兩者不存在固定的一對一關係，例如一個擠製編號可能對應兩個 T4 爐號，也可能只出現其中一種編號。因此，現行成對資料模型會讓使用者誤以為兩欄具有關聯，無法正確表達實際追溯資料。

本次將「爐具編號」在資料欄位、API 與畫面統一命名為「T4爐號」，並把擠製編號與 T4爐號改為兩份完全獨立的有序清單。

## 目標

- 一筆機械性質檢驗可分別保存零筆或多筆擠製編號與 T4爐號。
- 兩份清單各自新增、刪除、排序，不保存彼此的對應關係。
- 同一清單內的相同編號只保存一次。
- 既有資料安全拆分並去除因舊成對模型產生的重複值。
- 新舊前端短暫並存時，舊 `batches` payload 仍可被後端轉換。
- 清單、明細與稽核資料能明確顯示兩種追溯編號。

## 非目標

- 不建立擠製編號與 T4爐號的關聯表。
- 不推導某個擠製編號實際對應哪些 T4爐號。
- 不改變機械性質量測、規格下限、NG 判定或審批流程。
- 不新增其他追溯編號類型。

## 方案決策

採用單一「機械性質追溯編號」子表，以受控類型區分「擠製編號」與「T4爐號」。

此方案比沿用成對批次欄位更符合實際資料語意，也比建立兩張結構相同的子表更容易維護。新增其他編號類型時仍須另行提出設計變更，不在本次自動開放任意類型。

## 資料模型

新增 `機械性質追溯編號`：

| 欄位 | 型別 | 規則 |
|---|---|---|
| 識別碼 | Integer PK | 自動產生 |
| 機械性質檢驗_ID | Integer FK | 必填，刪除主檔時 cascade |
| 類型 | VARCHAR(20) | 必填，只允許 `擠製編號`、`T4爐號` |
| 序號 | Integer | 必填，必須大於等於 1 |
| 編號 | VARCHAR(100) | 必填，儲存前去除首尾空白 |

資料庫約束：

- `UNIQUE (機械性質檢驗_ID, 類型, 序號)`
- `UNIQUE (機械性質檢驗_ID, 類型, 編號)`
- `CHECK (序號 >= 1)`
- `CHECK (類型 IN ('擠製編號', 'T4爐號'))`
- `CHECK (length(btrim(編號)) BETWEEN 1 AND 100)`
- 對 `機械性質檢驗_ID` 建立索引。

ORM 新增 `MechanicalTraceNumber`，主檔關聯名稱為 `trace_numbers`。既有 `MechanicalBatch` 與 `batches` 關聯在 Migration 42 完成後停止使用。

## Migration 42

Migration 42 必須在單一 transaction 中執行，不得在驗證失敗時留下部分搬移結果。

執行流程：

1. 確認舊 `機械性質批次` 存在且新 `機械性質追溯編號` 不存在；若新表已存在且舊表已移除，視為已完成並安全結束。
2. 若新舊兩表同時存在於 migration 開始前，立即中止，要求人工確認，避免覆寫不明狀態。
3. 建立新表及受控約束。
4. 從舊表的非空 `擠製編號` 建立 `擠製編號` 明細；以去除首尾空白後的值去重，保留依舊 `序號`、`識別碼` 排序後第一次出現的值。
5. 從舊表的非空 `爐具編號` 建立 `T4爐號` 明細，採相同去重及排序規則。
6. 每種類型重新編定連續序號 `1..n`。
7. 以 distinct、trimmed value 集合進行雙向 `EXCEPT` 比對；任何缺漏或額外值都中止並 rollback。
8. 確認新表每種類型的筆數等於舊表相對欄位的 distinct 非空值筆數。
9. 驗證成功後移除舊 `機械性質批次` 表。

因舊成對模型可能重複保存同一擠製編號，本次依核准需求將同類型相同編號正規化為一筆；不同編號不會被刪除或合併。

## API 契約

新版 create/update payload：

```json
{
  "extrusion_numbers": [
    {"序號": 1, "編號": "E001"}
  ],
  "t4_furnace_numbers": [
    {"序號": 1, "編號": "T4-01"},
    {"序號": 2, "編號": "T4-02"}
  ]
}
```

使用新版格式時，兩個欄位都必須存在且必須是陣列；可為空陣列。每份陣列的序號必須為從 1 開始的連續正整數。使用 deprecated 舊格式時可只提供 `batches`，不得混用新版欄位。

後端在 Phase 1.1 保留舊 `batches` payload 相容處理：

- 將每列非空 `擠製編號` 收集到擠製編號清單。
- 將每列非空 `爐具編號` 收集到 T4爐號清單。
- 依舊序號排序、trim、去重後重新編號。
- 同一 request 不得同時送新版陣列與舊 `batches`，否則回傳 400，避免來源歧義。
- 舊 payload 相容行為標記為 deprecated；移除須另行提出變更。

新版 detail response 回傳：

```json
{
  "extrusion_numbers": [
    {"識別碼": 1, "序號": 1, "編號": "E001"}
  ],
  "t4_furnace_numbers": [
    {"識別碼": 2, "序號": 1, "編號": "T4-01"}
  ]
}
```

為支援舊前端短暫並存，detail response 同時保留 deprecated `batches`：

- 擠製編號與 T4爐號各自輸出為只有一個欄位有值的列。
- 不把不同類型重新配對。
- 新前端不得讀取 `batches`。

清單 response 增加 `T4爐號` 摘要；`擠製編號` 與 `T4爐號` 都依各自序號使用 `、` 串接。

## 驗證與錯誤處理

下列情況回傳 400：

- 新版欄位不是陣列。
- 陣列元素不是物件。
- 序號不是正整數、重複或不連續。
- 編號不是字串、trim 後為空或超過 100 字元。
- 同一清單內 trim 後編號重複。
- request 同時包含新版陣列與舊 `batches`。
- 舊 `batches` 結構不合法。

同一清單的重複判定採 trim 後的精確字串比對；不自動改變大小寫。

Service 在 commit 失敗時必須 rollback。真正資料庫或伺服器錯誤維持 500，不可誤報為驗證錯誤。

## 前端設計

新增／編輯表單把舊「擠製編號／爐具編號（可多組）」區塊改成兩個獨立面板：

### 擠製編號

- 顯示一份獨立有序清單。
- 提供「新增擠製編號」按鈕。
- 每列包含序號、輸入框與刪除按鈕。
- 刪除後自動重新編號。

### T4爐號

- 顯示一份獨立有序清單。
- 提供「新增T4爐號」按鈕。
- 每列包含序號、輸入框與刪除按鈕。
- 刪除後自動重新編號。

桌面版兩個面板並排，窄螢幕上下排列。新表單各顯示一筆空白輸入；送出時空白列不進入 payload，因此允許只有其中一份清單有資料，也允許兩份皆空。

同一清單出現重複編號時：

- 重複欄位顯示可存取的錯誤訊息。
- 設定 `aria-invalid` 與有效的錯誤描述 ID。
- 禁止儲存並顯示明確提示。

編輯時分別 hydrate 兩份清單，不在任何畫面暗示兩種類型存在配對關係。

清單頁增加「T4爐號」摘要欄，並把既有 `T4`、`T6` 標題改為「T4溫度/時間」、「T6溫度/時間」。

## 測試策略

### Migration

- 舊資料一列含兩種編號時拆成兩筆。
- 同一擠製編號搭配兩個 T4爐號時，擠製編號去重、兩個 T4爐號皆保留。
- 空白值不搬移。
- 每種類型序號連續且順序穩定。
- distinct 集合不一致時 transaction rollback。
- 新表已存在、舊表已移除時可安全重跑。
- 新舊兩表同時存在的非預期狀態會中止。
- 在 PostgreSQL 實際套用後查核表、約束、索引與資料集合。

### Backend

- 新版 payload create、update、detail、list。
- 只有擠製編號、只有 T4爐號、兩者皆空。
- 舊 `batches` payload 拆分與去重。
- 新舊 payload 同時存在時回 400。
- 重複、序號間斷、型別及長度錯誤回 400。
- 更新時正確取代兩份清單且 transaction rollback 有效。
- 刪除主檔時 cascade 刪除追溯編號。

### Frontend

- 兩個面板可各自新增、編輯與刪除。
- 操作其中一份清單不影響另一份。
- payload 組裝與 detail hydrate。
- 重複值提示、ARIA 連結與儲存阻擋。
- 空白列不送出。
- 清單摘要與欄位標題。
- 桌面／窄螢幕沿用 React Bootstrap 響應式格線。

### 完整驗證

- `venv\Scripts\python.exe -m pytest backend\tests -q`
- `npm test -- --run`
- `npm run lint -- --max-warnings=0`
- `npm run build`
- `git diff --check`
- 瀏覽器端到端建立「1 個擠製編號＋2 個 T4爐號」、重新載入編輯、刪除其中一個 T4爐號並確認清單摘要。

## 驗收標準

- 使用者能分別新增任意數量的擠製編號與 T4爐號。
- 一個擠製編號可與多個 T4爐號共同存在，畫面與資料都不建立配對。
- 同一清單內不會保存重複編號。
- 既有編號完整搬移，只有核准的同類型重複值會被正規化。
- 新舊 payload 相容期間不會產生假配對。
- 合併前所有 migration、後端、前端、lint、build 與端到端驗證均通過。
